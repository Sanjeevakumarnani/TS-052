## Your role and objective

You are the lead full-stack engineer, product architect, geospatial engineer, AI/vision integration engineer, database engineer, security engineer, QA engineer, and UI/UX designer. You must work **directly in the existing InfraPulse codebase**. The current app is an MVP, not a blank project. The repository is the existing `InfraPulse_MVP` project. Read the existing code before changing it. The exact current files and contracts are the source of truth. Do not blindly replace the application or build an unrelated application.

**Primary product objective:** Admins upload structured CSV records describing infrastructure assets, public works, development projects, service improvements, and claimed completion/status for each village. Users sign in, select State → District (if used) → Mandal/Block → Village, share device location, and can be associated with that village only when the location matches a supported official village boundary or a documented, configurable approximation. The user reviews/edits the AI analysis, then submits it. All reports and evidence are stored in the database and linked to the exact imported development record and village. Admins can inspect individual submissions, compare responses across residents, see discrepancies and summary calculations, review the AI output, and explicitly approve/reject findings. Only approved, validated evidence may affect trusted summaries or scores. The workflow must be functional from frontend through backend, database, storage, AI provider, tests, and documentation.

Do not only explain, plan, or generate mock screens. Implement the features in code, run the tests/build, and fix issues. Never report success for a feature that is only a UI placeholder.

## 3. Geographic hierarchy and location verification

### Required hierarchy

Store a canonical location structure, ideally with stable IDs rather than relying on village names alone:

`State → District (when applicable) → Mandal/Block → Village`

Names can repeat across districts/states. The foreign-key relationship must use IDs; imported data must resolve each development record to exactly one village ID. Support aliases/transliterations if feasible, but never silently assign an ambiguous village by name only.

### Location reference data

Inspect the current village data. Existing seeded village names and coordinates are synthetic demo data. Never treat them as official geography. Add a clear `is_demo`/`data_origin` distinction or equivalent. Admins must be able to import or configure verified geographic references, including official village/administrative codes, centroid coordinates, and ideally boundary polygons (GeoJSON) where lawfully available.

### Location permission and matching workflow

1. User creates/signs into an account.
2. User selects State, District (if present), Mandal/Block, and Village from controlled cascading selectors.
3. Explain in plain language why location permission is requested. Do not request browser geolocation before explaining the reason and asking the user to press a clear action such as **Verify my location**.
4. On that action, use the browser Geolocation API and capture latitude, longitude, reported horizontal accuracy, client timestamp, and the server receipt time. Request high accuracy where supported, with timeout/error handling.
5. Prefer point-in-polygon matching against a verified official village boundary. If that boundary is unavailable, use an explicitly configured distance threshold from a verified village centroid, with a warning that centroid/radius matching is an approximation. Do not invent boundaries or treat approximate/demo pins as official.
6. Compare the current coordinates to the chosen village and show a human-readable result: match, mismatch, not enough accuracy, unsupported location data, boundary unavailable, permission denied, or retry required. Explain approximate distance where appropriate, but do not reveal another user's location.
7. If match passes the configured rule, create a village membership/association with match method, coordinates (or appropriately minimised location record), accuracy, timestamp, and result. Do not call it “verified resident” if GPS alone only verifies presence near the village at that time. Label it “location matched” or similar.
8. If location mismatches, do not register the user to the selected village. Offer retry, reselect correct village, or a clearly labelled manual review process if a legitimate exception is needed. Manual overrides require an authorised reviewer and audit entry.
9. If the user refuses location permission, do not spoof success. Explain that location-based village association cannot be completed. Depending on product policy, allow general browsing but require a successful match or an approved manual process before submitting “verified village member” contributions.
10. Avoid storing precise location forever when unnecessary. Store the minimum needed evidence and show the location retention policy. Provide consent and account/data deletion processes as appropriate.

Do not claim browser GPS is tamper-proof. GPS can be inaccurate or spoofed. Location match only establishes a signal of presence and is one evidence factor, not proof of identity or residency.

## 6. Live camera capture with latitude/longitude overlay (not file upload)

Build this as a working browser camera flow, not a decorative screen.

### Capture lifecycle

1. User presses **Capture evidence** and sees why camera and optional location permissions are needed.
2. Check `navigator.mediaDevices.getUserMedia` availability and secure context. Localhost is generally permitted; a deployed production site must use HTTPS. Explain that restriction if the browser environment blocks camera access.
3. Request the rear-facing camera where possible (`facingMode: environment`) and provide a switch camera control when multiple cameras are available. Provide cancel/stop-camera controls and always release media tracks when closing/navigating away.
4. Concurrently obtain a fresh geolocation reading (if consented), with accuracy radius and timestamp. Don't silently reuse stale coordinates. If geolocation is absent/denied, do not display invented values; show “Location unavailable” and follow the configured policy (normally let the user retake/request permission; only allow a no-location contribution if the product's explicit fallback rules permit it, with lower evidence status).
5. Overlay **Latitude**, **Longitude**, **GPS accuracy**, and capture time visibly at the **bottom of the live camera preview**, as requested. The text must be readable, high-contrast and responsive. If no valid reading exists, show an honest unavailable state instead of fake coordinates.
6. On capture, draw the live video frame into a canvas to create a Blob/File in memory. Do not open a system file-picker for this primary flow. Let the user preview, retake, and confirm. Keep camera preview metadata separate from the image itself as structured data. Optionally generate a visible coordinate/time-stamped evidence copy for preview, but do not pretend a visual stamp is tamper-proof. Do not rely on EXIF alone for GPS.
7. Send the captured image Blob and metadata to the backend via multipart/form-data. Include project record ID, selected village ID, observation, client capture time, latitude/longitude, accuracy and consent flags. The backend must add its own receipt timestamp. Avoid including user identity/precise coordinates in public image URLs or exports.
8. Validate server-side: image format/content, file size, dimensions, decode success, and safe storage key. Reject corrupted, huge or unsupported files. Re-encode accepted images to a safe format if a suitable library is already available. Strip unnecessary embedded metadata where appropriate. Store files outside the public frontend directory and keep attachment access protected.
9. Show upload progress, retry, error and success states. Never report successful evidence submission before the API confirms it.
10. Store the image and metadata securely with the submission. Make access available to its owner and authorised admins/reviewers only. Do not create a public unauthenticated file URL.

### Browser and privacy edge cases

Handle camera denied, location denied, unsupported camera API, no camera, insecure origin, permission timeout, lost stream, upload error, poor GPS accuracy, browser refresh, and mobile rotation. Give actionable, human-readable messages. Explicitly ask permission before accessing camera/location. Do not activate camera or location on page load. Don't collect continuous background location; one current point at user action is sufficient.

A GPS overlay is a convenience/evidence label, not cryptographic proof. Show the GPS accuracy circle and do not claim precise verification when accuracy is poor.

## 7. Backend AI image-analysis workflow

The image must be analysed server-side by a real configurable vision model/provider, never by exposing a provider secret in frontend code. Use a provider abstraction so a compatible vision-capable API can be configured through environment variables. Inspect existing dependencies and choose the smallest maintained approach. Do not invent a provider call or return hardcoded fake analysis as if it were real.

### Required flow

1. The frontend submits the user's selected record, reported project status, observed status, optional notes, captured image, village ID, image capture coordinates/accuracy/time, consent, and evidence reference.
2. Backend verifies authentication, village membership/match, permission, input lengths, file validation, and record access.
3. Backend stores the submission and privately stores the image before/while starting analysis. Use an `analysis_status` such as `pending`, `processing`, `complete`, `failed`, `not_configured`. Handle retries idempotently so repeat requests do not create duplicate submissions.
4. Backend prepares a minimal context for the vision model: the admin-provided project claim/record details, the user's declared observation and the image. Send only necessary data; don't send unnecessary identifiers or user secrets. Ensure consent and privacy notice are recorded.
5. Ask the model for **structured JSON** only, with fields such as:
   - `summary`
   - `visible_elements` (observed visual features only)
   - `relation_to_claim` (`supports`, `partially_supports`, `contradicts`, `inconclusive`, `not_relevant`)
   - `apparent_condition` (`appears_functional`, `appears_incomplete`, `appears_damaged`, `not_assessable`, `not_applicable`)
   - `observations`
   - `uncertainties_and_limitations`
   - `possible_privacy_or_safety_issue`
   - `recommended_human_review`
   - `model/provider name and version` where actually known
   - `analyzed_at`
   Do not let a model invent latitude/longitude, infer exact village identity from the image, declare the photo authentic, prove completion, prove ownership, or claim engineering-grade condition from a single image. The model may say a visual appears consistent/inconsistent with a claim, but must clearly state limitations.
6. Validate the returned JSON using Pydantic or equivalent. If invalid, retry safely once or mark analysis failed; don't crash the submission workflow.
7. Store the original user response, image metadata, exact record ID, AI output, provider/model metadata, prompt/method version if safe, and timestamps as separate fields. Preserve the user's own answer and the AI output separately; never overwrite one with the other.
8. Show the AI result to the user before final submission, or if the chosen UX submits first, provide an explicit follow-up review step. User must be able to accept, edit, or disagree with the AI summary, with final user decision recorded separately from raw AI output. The user should not be forced to accept an incorrect AI answer.
9. AI output is **advisory only**. It must not auto-verify the report or directly change trusted development status, reliability score, ranking or funding recommendations. Only review/validation workflow can promote evidence into an indicator.
10. If the model/API key is not configured, times out, rejects the image, reaches rate limits, or returns errors, save the report and show `AI analysis unavailable` with a reason-safe message and retry option. Never display a hardcoded model result or claim that AI ran when it did not. A human-only submission path should remain usable, with analysis explicitly marked unavailable.
11. Add configurable rate limits, request timeouts, payload limits, cost guards and a secure environment configuration guide. Keep model/API key backend-only. Avoid logging base64 image data or secrets.

Create `.env.example` additions with documented, non-secret placeholders appropriate to the selected provider (for example API key, model name, API base URL only if genuinely supported, timeout, max image size). Never commit a real key. If image analysis is asynchronous, expose a status endpoint and implement polling/backoff or equivalent UX.

## 10. Calculation logic and how community evidence contributes

Keep the current five dimensions and the existing score engine unless audit identifies a defect:

- Digital connectivity: 25% prototype weight.
- Electricity: 20%.
- Roads: 20%.
- Public digital infrastructure: 15%.
- Essential-service access: 20%.

Weights and thresholds are prototype assumptions, not official standards. Missing values remain unknown, not zero. Keep the configured minimum valid weight/coverage threshold; current spec uses 60%. Label all synthetic records as demo.

Do not collapse **development-project status** into **service reliability**. A road repair marked “completed” is not by itself proof that the road is currently accessible and reliable; a public facility's existence is not proof it is operating; a single network photo does not measure speed or uptime. Maintain distinct concepts:

1. Admin-reported development/work status.
2. Resident-reported observed status.
3. AI advisory assessment.
4. Moderation/verification status.
5. Trusted indicator used in a reliability calculation, with method/source/time/unit.

Create transparent village-level verification metrics such as:

- Imported development-record count.
- Response coverage = distinct development records with at least one valid response / eligible imported records.
- Agreement rate among reviewed/eligible evidence, with sample size.
- Discrepancy rate for claims marked completed/operational but reported incomplete/damaged/not found, showing exact numerator/denominator and review status.
- Evidence recency and coverage.
- Count of awaiting review.

These are evidence/verification metrics, not automatically reliability scores. Clearly distinguish submitted from reviewed data. Avoid letting repeated reports from one person or one device dominate. Use deduplication, per-record rate limits, minimum sample sizes and a documented method for aggregation.

The official reliability score should change only if an authorised workflow explicitly promotes a validated indicator/value with an appropriate definition, unit, observation period, geographic scope and source. Save the score snapshot and method version. Provide an explanation of the change and preserve the previous result. AI confidence alone must never make a record verified.

If a basic consensus calculation is used for prototype insights, document it, include sample counts and confidence limits, and label it exploratory. Do not use unreviewed user answers to claim that a village is officially deficient or that public funds should be directed there.

## 12. Authentication and security

- Use a maintained password hashing library (Argon2/bcrypt suitable to the dependency stack). Never store plaintext passwords.
- Never hardcode production admin credentials. Use an environment-only local bootstrap mechanism to create the first admin, with instructions to disable/remove bootstrap after setup. Don't ship a working default password.
- Choose a coherent session approach; prefer secure, HttpOnly, SameSite cookies when compatible with the app architecture, and CSRF protection where needed. If bearer tokens are selected, document storage risks and avoid putting long-lived secrets in localStorage.
- Enforce roles and ownership on every protected endpoint: public users cannot see all reports, other users' submissions or private camera files; only admins can import or moderate.
- Validate all text, ids, enum values, file contents, coordinates, timestamps, row counts and file sizes on the server.
- Configure CORS for known origins; don't use wildcard origins with credentials.
- Add login and report-submission rate limits appropriate to the current stack; explain local/production configuration.
- Avoid detailed stack traces to API consumers. Do not log passwords, auth tokens, raw image/base64 payloads or private user location.
- Restrict uploads to accepted raster image types; never allow HTML/JS/SVG or executable uploads through this path. Use random storage keys, content validation/re-encoding, size caps, and private download endpoints. Use malware scanning if actually configured; otherwise do not claim files are scanned.
- Include a privacy notice, informed consent text for camera/location/AI processing, retention guidance, and a report of what fields are saved.
